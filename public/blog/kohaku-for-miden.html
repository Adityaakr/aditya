Privacy · Miden · ZK

Kohaku for Miden

Underneath the SDK surface: the protocol contracts, the post-quantum account, the providers, the plugins, and the Miden version of each.

Kohaku is an orchestration layer over several shielded-pool protocols, each of which is a tower of contracts: commitments, nullifiers, Merkle trees, and SNARK verifiers. On Miden, much of that machinery moves into base-layer primitives: private accounts, private notes, nullifiers, and client-side proving. This guide goes component by component, with illustrative code on both sides. Building Kohaku for Miden is less about porting contracts than re-expressing the same guarantees with primitives Miden already has.

01

What this covers, and the one reframe

Kohaku does not invent privacy. It orchestrates existing protocols (Railgun, Tornado Cash, Privacy Pools) and adds a post-quantum account, a verifying provider layer, and a plugin system a wallet can adopt piece by piece.

Each of those privacy protocols is, underneath, a set of on-chain contracts: a Merkle tree of commitments, a set of spent nullifiers, and a zero-knowledge verifier. That is the part that changes most on Miden. Miden gives you private accounts, private notes, commitments, nullifiers, and client-side proofs as base-layer features. So the contract stack that Kohaku spends most of its effort wrapping is, on Miden, mostly already there.

The familiar picture. This guide is the detailed version of the right-hand side, one component at a time.

02

The shared anatomy of a shielded pool

Railgun, Tornado, and Privacy Pools differ in features, but they share one skeleton. Understanding it once explains all three, and explains exactly what Miden replaces. A shielded pool is a contract that holds three things: a Merkle tree of commitments, a set of spent nullifiers, and a proof verifier. You deposit by adding a commitment. You withdraw by proving, in zero knowledge, that you own a leaf and have not spent it.

solidity
// the canonical shielded-pool shape, simplified (Tornado-style)
contract ShieldedPool {
    mapping(bytes32 => bool) public nullifierSpent; // double-spend guard
    bytes32[] public roots;                         // recent Merkle roots
    IVerifier public verifier;                      // a Groth16 verifier

    // deposit: insert a commitment as a new leaf in the Merkle tree
    function deposit(bytes32 commitment) external payable {
        require(msg.value == DENOMINATION);
        _insert(commitment);                        // updates tree + root
        emit Deposit(commitment, nextIndex);
    }

    // withdraw: prove you own a leaf, reveal only its nullifier hash
    function withdraw(bytes calldata proof, bytes32 root,
                      bytes32 nullifierHash, address payable to) external {
        require(isKnownRoot(root), "bad root");
        require(!nullifierSpent[nullifierHash], "already spent");
        require(verifier.verify(proof, root, nullifierHash, to), "bad proof");
        nullifierSpent[nullifierHash] = true;       // burn the note
        to.transfer(DENOMINATION);
    }
}

Every privacy protocol in Kohaku is a richer version of that contract, and every line of it is something a team has to deploy, audit, and maintain. Here is the part that matters: Miden provides all three pieces natively. A private note is a commitment in the chain's note tree. The nullifier is computed by the transaction kernel when you consume the note. And the client-side STARK proof replaces the SNARK verifier. You write no pool contract at all.

One scope note up front - Everything in this guide describes Miden's local transaction path: you execute and prove on your own device, and the node verifies the proof. That is the path private transfers use, and it is where "no verifier contract" and "no relayer" hold. Miden also defines network transactions, executed and proved by the operator for shared public state (live on testnet and still maturing). Read the claims below as scoped to the local path, not to every transaction Miden will run.

The left side is a contract you deploy and maintain. The right side is the Miden base layer.

A note on the code: the Miden snippets are illustrative and version-sensitive. They target @demox-labs/miden-sdk (~0.12); the SDK has since moved to the official @miden-sdk/miden-sdk (0.15+) with a newer MidenClient API, so check the current docs for exact signatures. One naming note that trips people up: the native signature the 0.12 code below calls RPO-Falcon512 (scheme id 0 in that SDK's newWallet) is now documented as Falcon-512 over Poseidon2, and the current Rust/auth surface numbers it differently (1 = ECDSA, 2 = Falcon-512). Same signature, renamed hash and a different id space. The goal here is the protocol mapping, not copy-paste production code.

// on Miden you deploy none of that. a private transfer IS the pattern:
// the note is the commitment, the nullifier is native, the proof is the STARK.
// build a private-note send request, then submit it (NoteType.Private
// means the note details stay off-chain; the commitment, plus the note's
// public metadata, is what lands on-chain).

  wallet.id(), recipientId, faucetId, NoteType.Private, 100n);
const txId = await client.submitNewTransaction(wallet.id(), req);
// consuming the note nullifies it; the kernel computes the nullifier from the
// note's own components (serial number, script, inputs, assets). no nullifier mapping
// for you to deploy, and no verifier contract: the client-side proof is checked
// by the network itself.

A note is the single primitive that replaces most of the pool-contract machinery: it carries assets, an executable script, the inputs that script reads, and a secret serial number, plus public metadata (sender, note type, tag) and up to four attachments. For a private note the details stay off-chain and only the note hash is published, but the metadata is always public, and attachment contents are stored on-chain even for a private note. That is a real privacy boundary: what you put in metadata or attachments is visible regardless of note type.

miden note model
// what "a note" actually is on Miden (the fields the commitment is built from):
//   assets     - the fungible / non-fungible assets the note carries
//   script     - MASM code that must succeed for the note to be consumed
//   inputs     - data the script reads, e.g. the recipient id
//   serial_num - a secret that makes the nullifier unlinkable
//   metadata   - sender + note type + tag + attachments; ALWAYS public
//
// commitment ~ hash(recipient, asset_commitment)   <- illustrative; note identity was
//              reworked in a recent release, so check the current docs for exact fields.
// nullifier  <- derived from the note's own components (serial_num, script_root,
//              inputs, assets): you must know the full note to compute it.
//
// for a PRIVATE note the details (assets, script, inputs, serial) stay off-chain;
// only the commitment and (on spend) the nullifier are published. metadata AND any
// attachments stay public, on-chain, even for a private note. (node-operator trust
// on the current testnet: see "the honest limit".)
On Ethereum a privacy protocol is a contract that re-implements commitments, nullifiers, and a verifier on top of a transparent chain. On Miden those three are the chain. So Kohaku for Miden is mostly fitting each protocol's behaviour to the native note model, not redeploying its contracts.
03

Railgun, in depth

Railgun is the protocol Kohaku ships first, and the one worth seeing in detail. Its structure is what you are mapping. Railgun has two main contracts: RailgunSmartWallet, the shielded pool that holds commitments and nullifiers and verifies proofs, and RelayAdapt, a helper that wraps and unwraps native ETH to WETH and composes actions with a multicall.

3.1 the account four keys, one 0zk address

A Railgun account is not an Ethereum account. From one credential it derives four keys, each with a distinct job, and encodes two of their public halves into a Bech32m address.

kohaku · ts
// illustrative API. the real @kohaku-eth/railgun surface is WASM bindings
// plus a RailgunSigner / RailgunAddress; the names here are schematic.
import { RailgunAccount } from "@kohaku-eth/railgun";

// a Railgun account derives its keys from two roots (spending + viewing):
//   spending   - sign / prove ownership of your notes
//   viewing    - decrypt your notes' metadata (ECDH -> AES-GCM)
//   nullifying - derived from viewing; produces note nullifiers
//   master     - public identity (spending + nullifying), in the 0zk address
const account = await RailgunAccount.fromMnemonic(mnemonic, provider);

// the 0zk address is Bech32m (BIP350): version + masterPubKey +
// (chainId XOR "railgun") + viewingPubKey, ~73 bytes, prefix "0zk".
const addr = account.getRailgunAddress(); // 0zk1qy...

3.2 the operations shield, transfer, unshield

All three operations build notes and Groth16 proofs through one pipeline. Note selection gathers unspent input notes, creates a change note for the remainder, and a send note for the recipient. The on-chain commitment is encrypted (AES-GCM in the V2 note format, XChaCha20-Poly1305 in V3) under an ECDH shared secret derived from the recipient's viewing key, so only they can read it.

kohaku · ts
// illustrative: method names are schematic; the real surface is WASM bindings.
// shield: public ERC20 -> a private note. builds a ShieldNoteERC20 with your
// master public key, encrypts the note (AES-GCM) under your viewing key, and
// calls RailgunSmartWallet. native ETH is wrapped to WETH via RelayAdapt first.
const shieldTx = await account.createShieldTx(token, value);

// private transfer: 0zk -> 0zk. note selection picks unspent input notes,
// makes a change Note for you + a SendNote for the receiver, then transact()
// produces a Groth16 proof. unshieldType = 0, nothing leaves the private set.
const transferTx = await account.createPrivateTransferTx(token, value, "0zk1...");

// unshield: private -> public 0x. same proof machinery, unshieldType = 1.
const unshieldTx = await account.createUnshieldTx(token, value, "0xRecipient");

3.3 on Miden the pool collapses into the account

On Miden, the 0zk balance is just your private account. The four keys collapse to one Falcon key for signing. The other jobs do not vanish, they move off the key model and into the SDK: you still deliver the note details to the recipient over an encrypted channel, and discovery still runs over note tags. Shield, transfer, and unshield are three uses of the same native note.

miden · ts
// Miden: your private account IS your private balance. no pool, no 0zk address,
// no separate shield step. and post-quantum auth is native (RPO-Falcon512).
// auth_scheme_id 0 = the native RPO-Falcon512 auth component; init seed is a
// Uint8Array (or null). private storage keeps the account state off-chain.
const wallet = await client.newWallet(
  AccountStorageMode.private(), true, 0, seed
);

// "shield"   -> just receive value into the private account (consume a note)
// "transfer" -> create a PRIVATE note to the recipient
const req = client.newSendTransactionRequest(
  wallet.id(), recipientId, faucetId, NoteType.Private, value);
const txId = await client.submitNewTransaction(wallet.id(), req);

// "unshield" -> send to a PUBLIC account/note instead of a private one.
// the four key types collapse: one Falcon key signs; "viewing" becomes the
// note details you deliver to the recipient off-band (encrypted by you).
on Miden → RailgunSmartWallet, RelayAdapt, and the transact() Groth16 proof collapse into a private account, a private note, and a native client-side STARK proof.

3.4 what a private note is as an illustrative sketch

A note is a small MASM program. Here is a simplified sketch of it, pay-to-ID, close to what runs when the recipient consumes a private transfer: it checks that the consuming account is the intended recipient, then moves the assets into their vault. A privacy SDK ships notes like this so an app never writes MASM.

miden · masm
# illustrative / simplified, not stack-exact. the canonical p2id.masm reads a
# two-felt account id from the note's inputs and compares via account_id::is_equal.
use.miden::account
use.miden::account_id
use.miden::note

# Pay-to-ID: only the intended account can consume the note. this is the shape
# of what "a private transfer" runs on the recipient's side.
begin
    # read the target account id (two field elements: prefix + suffix) from
    # the note, then load both felts onto the stack
    push.0 exec.note::get_inputs drop

    # compare BOTH felts against the executing account's id
    exec.account::get_id
    exec.account_id::is_equal assert.err="P2ID: not the intended recipient"

    # move each asset the note carries into the account's vault
    #   (loop the note's assets -> call.wallet::receive_asset)
end
04

Tornado Cash, in depth

Tornado is the simplest shielded pool, and the clearest contrast. It adds two things to the base contract from section 2: fixed denominations, so every note in a pool is indistinguishable, and a relayer, so the person withdrawing never has to submit a transaction from their own address, which would otherwise need ETH and reveal them.

solidity
// Tornado's two additions over the base pool: FIXED denominations (so every
// note looks identical) and a RELAYER (so the withdrawer's address never appears).
function withdraw(bytes calldata proof, bytes32 root, bytes32 nullifierHash,
                  address payable to, address payable relayer, uint256 fee,
                  uint256 refund) external {    // refund: ETH sub-payment for gas
    require(isKnownRoot(root) && !nullifierSpent[nullifierHash]);
    require(verifier.verify(proof, root, nullifierHash, to, relayer, fee, refund));
    nullifierSpent[nullifierHash] = true;
    to.transfer(DENOMINATION - fee);    // recipient gets the rest
    if (fee > 0) relayer.transfer(fee); // relayer is paid out of the note
}

The relayer exists only because, on Ethereum, submitting a withdrawal is itself a public act tied to an address that needs gas. The anonymity set is the count of identical deposits not yet withdrawn.

4.1 on Miden no relayer, by construction

On Miden, the relayer problem largely vanishes. You prove the spend on your own device, and a withdrawal is just a fresh transaction against your own account, so there is no separate public actor whose address leaks. A fixed-denomination mixer becomes a note script that only accepts and releases equal-value private notes. No Tornado-style relayer is needed to hide the withdrawal address; an app may still use delegated proving or a transport service for fees and UX, but never to break the address link.

miden · masm
// Miden: you do not need a relayer. you prove the spend locally, and the note
// model already breaks the link (a withdraw is a fresh tx against your account).
// a fixed-denomination anonymity pool becomes a note SCRIPT that only accepts
// and releases equal-value private notes:
use.miden::note
use.miden::contracts::wallets::basic->wallet

# (sketch) accept only the fixed denomination, then route assets to the consumer.
# the anonymity set is everyone who has deposited an identical note.
on Miden → MerkleTreeWithHistory plus the Verifier plus the relayer. The tree and verifier are native; the relayer is unnecessary because proving is local and the note model breaks the link.
One honest nuance - An anonymity set still has to come from somewhere: many identical private notes. On Miden you get unlinkability from the note model by construction, but a large mixing set is still a function of how many people use the same denomination. The primitive is easier; the network effect is the same.
05

Privacy Pools and compliance

Privacy Pools is the most interesting of the three, because it answers the obvious objection to mixers. Instead of all-or-nothing anonymity, a withdrawal proves two things: that your note is in the pool, and that it is in an approved subset of the pool, an association set chosen to exclude known-bad deposits. You get privacy and provenance at once. You can also ragequit, withdrawing your own deposit with no association proof.

solidity
// Privacy Pools = a pool PLUS an approved association set. a withdrawal proves
// your note is in the pool AND in an approved subset (the ASP root), giving you
// privacy with provenance. you can also "ragequit" your own deposit with no ASP.
contract PrivacyPool {
    function withdraw(
        bytes calldata proof,
        bytes32 stateRoot,      // membership in the pool's commitment tree
        bytes32 aspRoot,        // membership in the APPROVED set (compliance)
        bytes32 nullifierHash,
        address recipient
    ) external { /* verify both roots + nullifier, then pay out */ }

    // exit your own deposit without the association-set proof
    function ragequit(bytes calldata proof, bytes32 nullifierHash) external { }
}
// the same goal appears as Railgun's PPOI (Private Proofs of Innocence): prove
// your funds are NOT in a known-bad set, without revealing which note is yours.

Two takes on the same idea sit underneath this: Privacy Pools' association sets (the ASP root) and Railgun's PPOI (Private Proofs of Innocence). Both let you prove your funds are not in a flagged set, without revealing which note is yours. This is the compliance-aware direction the whole space is moving in.

5.1 on Miden provenance in the note itself

Miden lets you express this logic in the note itself. Because a note carries an executable script and can call into other accounts with foreign procedure invocation, a note can require an inclusion proof, against an approved-set root held by a registry account, before it will release its assets. Compliance becomes a property the note enforces, not a gate a central pool keeps. Treat this as a design pattern rather than a shipped standard: FPI supports the read-only cross-account call it needs, but the full flow (where the association witness lives, how its freshness is checked, what the ragequit equivalent is) is still yours to specify.

miden · masm
# Miden: compliance lives in the note's own logic. a note script can require an
# inclusion proof that its provenance is in an approved set before it releases its
# assets, using foreign procedure invocation (FPI) to read an approved-set root
# from a registry account. the note refuses to consume unless provenance checks out.
use.miden::note
use.miden::tx

# read the approved-set root from the registry via FPI, verify an inclusion proof
# for this note's origin against it (passed in via the advice provider), then
# release the assets. compliance is enforced by the note, not a central pool.
on Miden → the PrivacyPool contract (withdraw + ragequit) plus its association sets. On Miden the approved-set check can be expressed in the note script plus FPI, so the note refuses to consume unless its provenance is approved.
06

Post-quantum accounts

This is the component closest to dedicated post-quantum account work, and the one where Miden has the biggest head start. Kohaku's pq-account is an ERC-4337 smart account whose signature check is a post-quantum scheme, Falcon or Dilithium (ML-DSA), verified by an optimized Solidity verifier instead of ecrecover. It also ships a killswitch to migrate an account from ECDSA to post-quantum, and per-signer spending policies.

The account itself overrides just one thing, the signature check. Here is that override, verifying a lattice signature where a normal account would call ecrecover.

solidity
// the ERC-4337 machinery pq-account plugs into. a UserOperation is a transaction
// the EntryPoint validates and executes on the smart account's behalf.
struct PackedUserOperation {
    address sender;           // the smart account
    uint256 nonce;
    bytes initCode;           // deploys the account if it does not exist yet
    bytes callData;           // what the account should do
    bytes32 accountGasLimits;
    uint256 preVerificationGas;
    bytes32 gasFees;
    bytes paymasterAndData;   // optional: someone else pays gas (gas abstraction)
    bytes signature;          // the post-quantum signature pq-account verifies
}
// EntryPoint.handleOps(ops, beneficiary): for each op, call validateUserOp()
// then execute callData. a separate off-chain bundler relays ops to the EntryPoint.
solidity
// Kohaku's pq-account: an ERC-4337 account that verifies a POST-QUANTUM signature
// instead of ECDSA. validateUserOp is called by the EntryPoint singleton.
contract PQAccount is BaseAccount {
    bytes public pqPublicKey;       // Falcon or Dilithium (ML-DSA) public key
    IPQVerifier public verifier;    // an optimized Solidity PQ verifier

    function validateUserOp(PackedUserOperation calldata op, bytes32 opHash,
                            uint256 missingFunds) external override
        returns (uint256 validationData)
    {
        // verify a lattice signature over the userOp hash (not ecrecover)
        if (!verifier.verify(pqPublicKey, opHash, op.signature))
            return SIG_VALIDATION_FAILED;
        _payPrefund(missingFunds);
        return 0; // 0 == valid
    }

    // PQ killswitch: migrate the active validator from ECDSA to post-quantum.
    // spending policy: enforce a per-signer cap inside the account itself.
}

On Ethereum this is real work: you need the EntryPoint singleton, a bundler, and an expensive on-chain lattice verifier. Account abstraction itself is a standard bolted on top of accounts that are otherwise just keys.

6.1 on Miden this is the default

Miden is post-quantum at its core. Every account is programmable. Account abstraction isn't a standard you opt into; it is how accounts work. The native signature is Falcon-512 (over Poseidon2 in current docs; the 0.12 SDK below calls it RPO-Falcon512). So the whole pq-account package reduces to choosing the native auth: no EntryPoint, no bundler, no Solidity verifier.

miden · ts
// Miden: post-quantum is the DEFAULT, not an add-on. RPO-Falcon512 is the native
// signature. there is no EntryPoint, no bundler, no Solidity verifier: account
// abstraction is simply how every Miden account works.
const wallet = await client.newWallet(
  AccountStorageMode.private(), true, 0, seed   // 0 = RPO-Falcon512 in this SDK (the Rust protocol enum numbers it differently)
);
const key = SecretKey.rpoFalconWithRNG(seed);          // native RPO-Falcon512 key
const commitment = key.publicKey().toCommitment();     // public key as a Word
const auth = AccountComponent.createAuthComponentFromCommitment(commitment, 0);

// the "spending policy" from pq-account becomes programmable auth: the account's
// auth code runs INSIDE the tx and, using transaction introspection, can read
// what is leaving the vault and abort if it is over a cap. (this is the Subrosa
// agent cap.) ECDSA is also supported when you must reuse existing keys.
on Miden → validateUserOp, the lattice verifier, and the spending policy collapse into native Falcon auth plus programmable auth that reads the vault and caps spend in-transaction.

6.2 the spending policy as native auth code

The per-signer spending policy that pq-account enforces in Solidity becomes a few lines of account auth on Miden. Because auth runs inside the transaction and can introspect what is leaving the vault, the cap is enforced by the chain, not trusted to the app. This is the exact mechanism behind a confidential agent that may trade up to a limit and no further.

    exec.account::incr_nonce

07

Private state and multisig

The last account-level capability is coordination. When two parties or two devices share private state, something has to keep them in sync and gather signatures. Kohaku approaches this through multi-key accounts and recovery. On Miden it becomes private-state sync plus threshold signing, and it is where the Guardian role lives. Miden supports async transaction execution: while the executor builds a transaction it can call back into an authenticator, and it can hand a transaction summary to several co-signers who each verify it against chain state before signing.

miden · ts
// Miden supports async execution: while building a tx the executor can call
// back into an authenticator (an external keystore). that callback is where a
// co-signer (a Guardian-style service) verifies the work and returns a signature.
// illustrative: the real surface is the SDK's external-keystore / sign-callback.

// 1. the executor produces a TransactionSummary describing the tx's effects
// 2. distribute the summary to the co-signers (it carries deltas, not keys)
// 3. each co-signer re-derives the summary, checks it against chain state, and
//    signs only if it matches; it never holds a key that can move funds alone
// 4. collect the threshold of signatures, attach them, and submit the tx
on Miden → Kohaku's multi-key accounts and recovery turn into private-state sync plus threshold signing through Guardian. Every co-signer is a verifier, never a custodian. Guardian is not custody, but it is still a trust boundary: it can affect liveness, and it may see submitted state payloads unless the deployment adds encryption or self-hosts.
Why this matters for the SDK - This is the piece that unlocks multi-party and multi-device apps: shared treasuries, social recovery, an agent whose large actions need a human co-sign. The SDK's job is to make a co-sign feel like one approval, while the Guardian never holds a key that can move funds on its own.
08

Providers and the connection layer

Kohaku treats the connection itself as a leak. Its provider package puts one interface over ethers, viem, helios, and colibri, with a strict hierarchy: a local node first, then your own RPC, then the Helios light client wrapping an untrusted RPC and verifying its answers on-device, and only as a last resort a default endpoint, with a warning. No single RPC should get to watch every balance query and tie it to your IP.

kohaku · ts
// Kohaku's provider: one interface over ethers / viem / helios / colibri, with
// a privacy hierarchy -> (1) local node (2) your own RPC (3) Helios light
// client wrapping an untrusted RPC and verifying it on-device (4) default (warn).
import { createProvider } from "@kohaku-eth/provider";
const provider = createProvider({ backend: "helios" }); // verify, don't trust

In code, that hierarchy is a verifying wrapper around an untrusted RPC, plus local token discovery instead of a centralized indexer.

kohaku · ts
// the connection-layer privacy, in code: wrap an untrusted RPC in Helios so every
// response is verified on-device (checkpoint sync), and discover tokens by scanning
// the user's OWN events locally instead of trusting a centralized indexer.
import { createProvider } from "@kohaku-eth/provider";
const provider = createProvider({
  backend: "helios",          // verify RPC answers locally, do not trust them
  checkpoint: TRUSTED_BLOCK,  // start from a recent trusted state, not genesis
});
const tokens = await provider.discoverTokensLocally(account); // no indexer

8.1 on Miden pull-only sync is a privacy lever, not invisibility

Miden's client is the provider, and its sync model is already a privacy feature. The node does not push you a feed. You pull notes that match your account's note tags and filter them locally. The tags are deliberately coarse: a tag can also match other users' notes, and that fuzziness is part of the privacy, while still giving you the local, indexer-free token discovery Kohaku has to engineer around centralized services. The remaining concern, not pinning a user to one observable endpoint, carries over to Miden's own node-trust and transport choices.

miden · ts
// Miden: the client is the provider, and tag-based pull sync IS private token
// discovery. the node never pushes your data; you pull notes matching your note
// tags and filter locally, so there is no centralized indexer watching balances.
const client = await WebClient.createClient(ENDPOINT);
await client.syncState(); // pulls notes matching your tags, then filters locally
on Miden → the provider abstraction plus Helios plus private token discovery. The verifying-provider idea carries over; pull-only, tag-based sync gives you more private discovery than a centralized indexer, though the endpoint still sees your requests.
09

The plugin system, and one surface

Kohaku is deliberately a modular toolkit with a plugin system: a wallet team takes the pieces it wants and leaves the rest, without rewriting its app. The same shape works on Miden. Each capability from this guide is a plugin behind one facade: protocol plugins (note scripts), account plugins (auth components), proving plugins (local or delegated), and provider plugins. The app sees one ergonomic call per intent.

The components from sections 3 to 7, as plugins behind a single surface.

kohaku-for-miden · ts
// the Kohaku-for-Miden facade (illustrative): each capability from this guide is
// a plugin behind one surface; the app never touches a note, proof, nullifier, or key.
class MidenPrivacy {
  constructor(client, o) { this.client = client; this.seed = o.seed; this.proverUrl = o.proverUrl; }
  static async connect(o) {
    const client = await WebClient.createClient(o.endpoint);
    await client.syncState();
    return new MidenPrivacy(client, o);
  }
  async createPrivateAccount() {                       // account plugin
    const wallet = await this.client.newWallet(
      AccountStorageMode.private(), true, 0, this.seed);  // 0 = RPO-Falcon512
    this.account = wallet.id();
    return wallet;
  }
  async privateTransfer({ to, token, amount, delegate = false }) {  // protocol plugin
    const prover = delegate
      ? TransactionProver.newRemoteProver(this.proverUrl)   // proving plugin
      : TransactionProver.newLocalProver();
    const req = this.client.newSendTransactionRequest(
      this.account, to, token, NoteType.Private, amount);
    // execute -> prove (local or delegated) -> submit
    const result = await this.client.executeTransaction(this.account, req);
    const proven = await this.client.proveTransaction(result, prover);
    return this.client.submitProvenTransaction(proven, result);
  }
  async balance(faucetId) {
    await this.client.syncState();
    const account = await this.client.getAccount(this.account);
    if (!account) throw new Error("account not found");
    return account.vault().getBalance(faucetId);
  }
}
The test of the whole thing - A developer writes privateTransfer({ to, token, amount }) and gets a private note, a client-side proof, and a commitment on chain. Everything in sections 2 through 7, the pool, the keys, the verifier, the relayer, the EntryPoint, the indexer, is either native or hidden inside the SDK. That gap is the product.
10

Best practices, in depth

These are drawn from Kohaku's own practices, re-grounded for Miden. Privacy tooling fails quietly: the code runs perfectly and still leaks what you meant to hide. Most of these are about the layers around the proof, not the proof itself.

10.1 Account isolation

Kohaku's strongest recommendation is one account per dApp, so activity in one place cannot be correlated with another. On Miden this is cheap: private accounts are easy to create, so make a fresh account per app or per role the default, and have the SDK remember which account belongs to which context.

10.2 The connection layer

Follow Kohaku's RPC hierarchy in spirit: prefer verification over trust. On Miden, lean on pull-only sync so no central indexer sees balances, and avoid pinning a user to a single observable node. Treat the endpoint as part of the threat model, not an afterthought.

10.3 Note and data handling

  • Default to private, choose public on purpose - Storage mode and note type are explicit. Private should be what happens when a developer does nothing.
  • Treat note delivery as part of the protocol - A private transfer is only private if the note details reach the recipient over an encrypted channel. Miden gives you two paths: a manual off-band side channel, or the note transport service the client already takes an endpoint for (createClient(rpc, noteTransport, seed)), which routes by tag and leaves encryption to you. Build one of them into the SDK; do not leave it as a manual step over a plain message. Note transport is its own trust boundary, distinct from the RPC node and the remote prover.
  • Mind metadata, not just contents - Timing and query patterns leak. Borrow Kohaku's private-discovery thinking even when the amounts are already hidden.

10.4 The honest limit

On Miden's current testnet the operator is centralized, so treat privacy against the node operator as not yet guaranteed. Rely on privacy between users today, not on privacy against the operator, until the network decentralizes. It's a deliberate guardrail while the network matures. Design the SDK around that, and never promise stronger privacy than the chain gives today.

10.5 Proving

  • Prove locally when you can; delegate when you must - Local proving keeps everything but the proof on the device. Fall back to a remote prover for weak devices or large transactions. A remote prover is trustless for correctness but sees your transaction inputs, so this is a privacy boundary: default the choice and abstract it in the SDK, but surface it, do not hide it from the user.
  • Only use multi-threaded proving when the page is cross-origin isolated - It needs COOP and COEP headers. If you cannot set them, stay single-threaded rather than break in production.
  • Show progress - Proving takes real time; never let a confirm step look frozen.

10.6 Keys, auth, and compliance

  • Use the post-quantum default - Falcon is native. Lead with it; add ECDSA only to reuse existing key material. Keep a migration path, the equivalent of pq-account's killswitch.
  • Push limits into account code - Spend caps and rate limits belong in the account's auth logic, enforced by the chain, not in your app where they can be bypassed.
  • Keep co-signers keyless - A Guardian-style co-signer should verify the transaction summary and sign, never hold a key that can move funds alone.
  • Make compliance opt-in and provable - Where provenance matters, use the association-set or PPOI pattern through the note script, so users prove innocence without revealing which note is theirs.

10.7 SDK design

  • Modular and optional, like Kohaku - Let a team adopt one plugin without taking all of them.
  • Sane defaults over options - Most leaks are missing flags, not wrong ones.
  • Wallet-agnostic building, one call per intent - The SDK builds and proves; the wallet signs and submits. If a private transfer is more than one obvious call, the abstraction is not finished.
11

Where to start

You do not build all of this at once. This order gets developers shipping fastest, with each step usable on its own.

  1. Client and accounts - The provider wrapper plus create-and-manage for private accounts with native Falcon auth. Nothing else is usable until this is smooth.
  2. Notes, transfers, and proving - One-call private transfers, encrypted off-band delivery, and a defaulted local-or-delegated proving choice (abstracted, but visible, since a remote prover sees your inputs). This is the Railgun and Tornado behaviour, on the native note model.
  3. Programmable auth - Account-level spend caps and rate limits via transaction introspection. This is pq-account's spending policy, native.
  4. Compliance and private state - Provenance in note scripts (Privacy Pools' association sets and Railgun's PPOI), plus shared private state and threshold signing through Guardian. This is Privacy Pools (and Railgun's compliance), on Miden.
  5. Reference app, plugins, and docs - A small private app built entirely on the SDK, the plugin interfaces other teams extend, and the tutorials that make them copy it. Subrosa is most of this proof already.

The component map again, now as a build sequence. Everything on the right is native or a thin wrapper.

The one-line version - A privacy protocol on Ethereum is a contract stack that rebuilds commitments, nullifiers, and a verifier. On Miden those become base-layer primitives. So Kohaku for Miden should not be a direct port of Railgun, Tornado, or Privacy Pools. It should be a developer-facing SDK that turns native private accounts, private notes, programmable auth, Guardian coordination, and client-side proving into one obvious product surface.
