Build Ethereum dApps That Feel Instant: A Practical Guide to Preconfirmations and Faster UX

A local lab that measures how fast a validator's signed promise arrives, how many one validator executes per second, how long Ethereum takes to settle the same write, and what a reorg does to a promise that has already been handed out.

Vara.eth lets a client send a transaction straight to a validator and get back a signed receipt with the program's reply, before anything touches Ethereum. The pitch is a wallet that feels instant while Ethereum settles in the background.

The question this lab asks is narrow: what does that receipt actually guarantee, and how fast is it on a real stack? To answer it I built a toy order book as a Sails program, a Node engine that writes through both paths and timestamps every hop on one clock, a committed view rebuilt only from Ethereum logs, and a harness that forces reorgs of chosen depth against nodes started with chosen quarantine settings. Every number below was produced by that stack. The Hoodi testnet was down during this work, so everything ran against a dev node with an embedded Anvil.

Terms used below
pre-confirmation: a validator's signature over a program's reply to a transaction. Returned in milliseconds, before any batch reaches Ethereum.
injected transaction: a transaction sent directly to the validator's RPC rather than through an Ethereum contract. This is the fast path.
Router / Mirror: the Ethereum contracts. The validator commits batches to the Router; each program has a Mirror where its events surface as logs and where L1 writes are sent.
canonical quarantine: how many blocks behind the Ethereum head the validator anchors its work. A node flag in this lab, set per run with --canonical-quarantine.
committed: the write's events are visible in Mirror logs on the Ethereum side. In this lab, that side is a local Anvil chain.
01

The problem

A pre-confirmation is a validator's signature over a reply. It is not a block, and it is not finality. Three things about it are easy to assert and hard to measure without a controlled setup:

  • Latency. On loopback the receipt arrives in single-digit milliseconds, which tells you nothing about a user on a real network. The wire needs to be put back, in a way that is measured rather than guessed.
  • Settlement. The validator commits batches to a Router contract on Ethereum, and the program's events surface as logs on its Mirror contract. Until that happens the pre-confirmed state exists only in the validator's memory. The lag has to be measured from a view that contains nothing the validator said.
  • Reorgs. The validator anchors its work to an Ethereum block. If that block is reorganised away, what happens to promises already issued, and does the validator keep issuing new ones?
02

Architecture

Four processes, one machine. The dev node spawns Anvil itself, deploys the Router, and runs a single Malachite validator. The lab server owns the Anvil dev keys, drives both write paths, and streams a snapshot to a browser page over WebSocket. Nothing in the browser is on the timing path.

The two views come from two different sources. Any divergence between them is a concrete, countable thing.

The order book program is deliberately small: place(side, price, qty), cancel(id), a book() snapshot, and a seq() counter. Every state change emits exactly one Ethereum-style event stamped with a monotonically increasing sequence number, so replaying the events reproduces the book. A second program, ledger, backs the wallet's Send tab with a one-time faucet and a balance-checked transfer. A third, counter, does one increment and emits nothing; it exists to measure execution throughput without event overhead.

03

How it works

Two write paths, one clock

An injected write goes to the validator over its RPC and resolves when the validator-signed receipt arrives. An L1 write is an ordinary Ethereum transaction to the program's Mirror contract and resolves when Anvil mines it. Both are timed with performance.now() in the same process. Signing and the reference-block fetch happen before the submit stamp on both paths, so neither is charged for work the other excludes.

That symmetry was not there in the first version: the L1 path signed inside its window and viem polled receipts every four seconds by default, which inflated the L1 numbers until both were fixed.

The committed view trusts nothing the validator says

The L1 watcher polls Anvil every 50 ms. Before ingesting a range it reads the hash of the top block, fetches the logs, then reads the hash again. If it changed, a reorg raced the fetch and the batch is thrown away. On every poll it also checks that the previously seen head is still canonical, and if not, it resets the book and re-ingests from genesis.

A rebuild clears every write record's committed timestamp, because a stamp that survives a rebuild is a stamp for a block that may no longer exist. The first reorg matrix I produced was wrong for exactly that reason, and a reviewer caught it.

Putting the wire back

Loopback flatters the headline number. The server therefore starts a WebSocket proxy in front of the validator RPC and, at startup, measures the median round trip of a JSON-RPC call to wss://rpc.vara.network. The "measured" profile delays every frame in each direction by half that round trip plus Gaussian jitter and a 2% chance of a spike.

Delays are order-preserving, and frames that arrived within 40 ms of each other keep their spacing, because compressing the validator's subscription acknowledgement into its first notification made the JS client drop the notification. Two to three percent of writes reported no receipt until that rule existed. From this machine the round trip calibrated between roughly 165 and 190 ms across runs.

Forcing reorgs

The reorg matrix restarts the node per cell with a chosen --canonical-quarantine, deploys a fresh program, commits three orders to Ethereum, pre-confirms two more without waiting for settlement, then calls anvil_reorg with a chosen depth, which drops and re-mines that many blocks empty. It sends one more write five seconds later and watches for forty seconds.

The harness records whether the in-flight orders are ever re-committed, whether the seeded orders come back, whether the post-reorg write settles, and whether the node log starts saying refusing to build batch.

Finding the execution ceiling

The live path is capped by the client, not the validator: a Node process signs about 290 injected transactions per second. To see what the validator itself does, a probe pre-signs a few thousand transactions to the counter programs, fires them with injected_sendTransaction and no per-transaction subscription, and reads the executed count back from the programs' own count() query each second. The number reported is executions the program performed, not submissions the RPC accepted.

Passkey signing

The wallet drawer derives a secp256k1 key in the browser from a WebAuthn PRF output through HKDF. The server builds and anchors the injected transaction, hands the hash to the browser, and receives only the signature back. The validator recovers an Ethereum address from that signature like any other.

The key never leaves the browser, and the passkey wallet is never funded with anything. Execution is paid from the program's own executable balance, which is one of the more interesting properties of the model and one of the easier ones to misread in a demo.
04

Hard decisions and what they cost

  • Timing lives in the server, not the browser. A browser-only dapp would have been more honest as a product but would have straddled two WebSocket clients in one event loop, pulled the Polkadot peer dependencies of sails-js into Vite, and made the headless benchmark a second implementation. The page is a viewer; the engine is where correctness lives.
  • Three fills per order. ethexe allows four outgoing messages per execution and every Ethereum event counts. An order that crossed four resting makers panicked with OutgoingMessagesAmountLimitExceeded, which reads as panicked with '<unknown>' unless the program is built with the gstd-panic-message feature. The book now performs at most three fills per order and rests the remainder, like a per-transaction match limit on a venue.
  • The dev node's store is never pruned. ethexe run --dev --tmp writes every micro-block to RocksDB and keeps it: 64 GB after 41 minutes at 25 tx/s, with micro-block cadence degrading from 10 ms to 80 ms. The server recycles node, Anvil, and deployments every 30 minutes or above 40 GB, never during a load test, and drops in-flight records at that moment because they cannot settle on the new chain. A latency-based trigger was tried first and looped at high rates because it could not tell store bloat from queueing.
  • A vendored, unpublished SDK. The server uses @vara-eth/api 0.6.0-rc.0 from the vara-wallet repository as a tarball. The version on npm today is 0.5.2. Against a v2.0.0 node the release candidate picks the legacy RPC envelope correctly but signs the legacy digest, and the node answers "Address mismatch". One property override on the transaction instance points the signer at the current hashable bytes. This is illustrative of the moment, not a stable API.
  • Initialisation is an L1 message. Creating a program only creates its Mirror. The program stays uninitialised until the first Ethereum-side sendMessage carries the constructor payload, and injected transactions to it are silently purged. The deploy script sends that message for every instance before anything else touches it.

One trial per cell. The boundary sits exactly at depth = quarantine + 1.

The rule that fell out: a reorg is absorbed if and only if its depth is at most the canonical quarantine plus one. Beyond that, the coordinator logs refusing to build batch and never recovers on its own. Previously committed orders whose commit transactions were reorged away are never re-committed. And the validator keeps issuing signed promises in milliseconds for new writes that will never settle.

On its own, a pre-confirmation carries no settlement guarantee. It is worth exactly as much as the depth of the validator's Ethereum anchor. That is the single most useful thing this lab produced, and it was cheap to hit.
06

What this does not show

  • One validator, one machine. In production the Router accepts a batch only when a threshold fraction of the validator set has signed it (see validatorsThreshold in IRouter.sol); latency, throughput, and failure behaviour with several validators will differ from one. The dev node's quarantine is a local knob, not a description of network policy.
  • Anvil is not Ethereum. "Committed on Ethereum" here means the Router on a local Anvil chain accepted the batch. Real L1 inclusion adds block time, gas markets, and its own finality timeline. Reorgs were forced with anvil_reorg, which drops and re-mines empty blocks; in a real reorg the displaced transactions usually return to the mempool and are re-mined rather than vanishing.
  • The order book keeps no balances. It is a matching engine with no money attached: anyone can sell a quantity they do not hold, and fills move nothing. Only the ledger program behind the wallet's Send tab enforces balances. This is fine for measuring latency and misleading in a wallet demo; making the book settle in ledger units is the obvious next change.
  • The emulated wire is a model. It reproduces a measured median round trip with jitter and spikes; it does not reproduce TLS, HTTP/2 multiplexing, packet loss, or a congested last mile. Numbers labelled "emulated" are exactly that.
  • One trial per matrix cell, and committed timestamps are observation times, which include up to one 50 ms poll interval and the getLogs round trip.
  • Tens of thousands of transactions per second were requested and not reached. The measured ceiling on this laptop and node version is a few hundred executions per second. Reaching 50,000 would require a validator set with parallel execution across many programs and machines and a node tuned for it; nothing here indicates whether that is feasible.
  • The SDK is a pre-release. The digest override described above works against gear v2.0.0 and will be wrong or unnecessary against a node that exposes the version RPC.

Reproducing it

Prerequisites: Rust with the pinned nightly, protoc, cmake, Node 22, sails-cli 2.0.0, and Foundry 1.7.0 exactly; the dev node refuses other builds.

Build the node, deploy the programs, start the lab
git clone --depth 1 --branch v2.0.0 https://github.com/gear-tech/gear.git gear
(cd gear && cargo build -p ethexe-cli --release)                 # about 25 min, once
for p in orderbook ledger counter; do (cd $p && cargo build --release); done
run/start-node.sh --quarantine 0 && run/deploy.sh                # node + Anvil, 5 book instances, ledger
(cd lab-server && npm install && npm run serve)                  # ws://127.0.0.1:8787, autopilot on
(cd lab-ui && npm install && npm run dev)                        # http://localhost:5173
Run the measurements
cd lab-server
npm run bench -- 30                       # both paths, per-hop latency, report under reports/
npm run reorg-matrix                      # quarantine × depth, restarts the node per cell
INSTANCES=16 EXEC_BALANCE=25000000000000000 ../run/deploy-counter.sh
npx tsx src/fire-cli.ts 3000 128 1 16     # pre-signed fire-and-forget, executed/s from the counter
08

What is next

  • Make the order book settle in ledger units: lock quantity or price × quantity at placement, move units on fill, unlock on cancel. The wallet then behaves the way a viewer assumes it does.
  • Run the same matrix and benchmark against Hoodi once the testnet is back, so the emulated wire can be replaced with a measured one and the quarantine rule can be checked against a real validator set.
  • Repeat each reorg cell several times and report variance rather than one trial.
  • Watch the ledger's Mirror as well as the book's, so wallet transfers get settlement stamps instead of being marked untracked.
