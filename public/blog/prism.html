Prism · Multi-Agent Harness for Claude Code

A multi-agent harness that measures its own value

A complete agent workflow, from reading a codebase to shipping and reviewing it, built on grounded claims, compounding memory, and enforced safety. And a rare experiment: does the fleet actually beat one careful pass?

01

The bet nobody checks

Most multi-agent AI tools rest on one assumption: if one model is useful, a coordinated group should be better. So people add roles. One agent plans, another critiques, another verifies, and the hope is that more perspectives produce a better answer.

It sounds right. Almost nobody checks.

Prism checks. It is a multi-agent orchestration harness for Claude Code: a set of slash commands that take a hard problem, split it across several agents that look at different evidence, judge where they disagree, verify the claims that matter, and loop until the answer settles. That much is familiar. What makes Prism unusual is the system around that loop. It remembers the project across runs, grounds every claim in real code, enforces its safety rules with hooks the model cannot skip, and ships a harness that measures whether the fleet actually beats a single careful pass.

When it ran that measurement on its own design, the result was uncomfortable. Across twelve real design tasks about Prism's own internals, one careful Opus pass beat the eight-agent setup five times, lost three, and tied four, at about 4.6 times fewer tokens.

Prism reports that plainly and keeps building from it. This article is about the whole system, not just the scoreboard. A strong model alone is already capable, so anything that wraps extra agents around it has to earn the cost and complexity it adds. Prism holds itself to exactly that standard.

02

The problem it starts from

One pass through a strong model fails in predictable ways. It anchors on the first plausible answer and never stress-tests it. Faced with two real but conflicting considerations, it averages them into a vague middle instead of deciding which one wins. It states things about your own code or a library's API that it never checked, and hands you the conclusion with no reasoning trail, so you cannot tell which parts to trust. It is stateless, relearning the same project facts every session. Its safety guidance is unenforced: text it can ignore three hundred lines in. And the usual multi-agent cure is unfalsifiable, because the tools selling it never measure whether the agents helped.

Each of those failure modes has a specific answer in the sections below. Two ideas organize the whole design: the agents are made to look at different evidence rather than wear different hats, and conflicts between them are decided, not blended into a vague middle.

The heavy commands (plan, build, implement, and feedback) all run on one shared engine, and /prism-ship chains them end to end. That engine is where most of Prism's interesting decisions live.

04

The deliberation engine

Every heavy command feeds the same pipeline: fan out across lenses, score how much they diverged, judge the results, verify the claims that matter, loop until the answer stops changing, and persist what was learned. Here is the lifecycle and the engine together.

The lifecycle feeds one shared engine; the engine reads and writes project memory; hooks and the proof harness sit alongside. Skeptics in the verify stage are 2 Opus and 1 Sonnet under majority rule.

Fan-out with differential context - This is what separates real diversity from theater: the lenses read different evidence, not the same context in different hats. The core lenses (first-principles, adversary, practitioner) stay holistic and look at the whole problem. The domain lenses are routed to the slice of code their concern owns: security reads auth, keys, and custody; regulatory reads the money-movement paths; data-integrity reads the schema and ledger; cost reads fees and infrastructure; UX reads the user flows. Each lens reports the exact file:line ranges it examined, and Prism caches that routing as a file concern map so it does not rediscover which files matter on every run.

Divergence score - Right after fan-out, Prism checks whether the lenses truly split or only appeared to. It scores two things: how much the lenses overlap in the code they cite (60% of the weight), and how much their conclusions differ (40%). Overlap is measured as Jaccard similarity, the shared cited lines over the combined set, and it carries the most weight because it directly tests whether the differential routing worked. If the lenses cited the same lines and reached the same conclusion, the extra agents added nothing, and Prism says so. The score prints on every run and flags when the diversity is only cosmetic. The threshold is a deliberate placeholder, set to 0.30 and marked uncalibrated until the proof harness derives a real cutoff from data.

Judge - The judge does not blend the briefs into an average. It produces a structured read: what the lenses agree on, where they contradict each other and which side is better supported, which insights only one lens caught, and which blind spots they all share. The output is a decision, not a merge.

Verify, in two checks - First, grounding. Every claim about the code has to cite a file:line, and a verifier re-opens that line to confirm it. Every claim about a library or API is checked against installed type definitions or official docs, never the model's memory. Second, adversarial review. Each load-bearing claim goes to a skeptic panel whose job is to refute it: two Opus instances for rigor and one Sonnet for independence, under majority rule. The lone Sonnet cannot sink a good claim on its own, but it can be the deciding vote on a flaw both Opus instances missed. Two of three votes kill a claim.

Loop and persist - Prism then re-attacks its own draft in critique mode, folds in only the fixes that survive, and repeats until a full round changes nothing material, capped at three rounds. The final result is saved to docs/, the project memory is updated, and telemetry records the divergence score, the model pool that ran, and how each claim survived.

One label matters here. Surviving the skeptics is marked cross-tier-survived, which ranks below grounded (re-checked against live code or docs). The panel uses different Claude tiers, not different model families, so it lowers the chance the reviewers share an error without removing the blind spots baked into Claude itself. Grounding outranks survival, and every decision doc says which is which. A lot of AI systems blur "we checked this" with "nobody objected to this." Prism keeps the two apart.

Two recent additions extend that engine to bigger, messier work. The first is a repo map for large codebases. Differential context only helps if the right files reach the right lens, which gets hard at scale, so Prism caches the project's structure, not its code claims, in .prism/repo-map.md: the directory tree, the workspace roots, and cheap concern tags. A sizing gate then picks the approach, with flat explorers under about 150 files, concern-bucketed fan-out up to 800, and a structure-map-first pass beyond that. Staleness is checked by git blob hashes rather than file counts, and ranking only decides how deeply a file is read, never whether it is read at all.

The second is a craft floor for code Prism writes on a blank page: intent-revealing names, one job per function, no dead code, and comments that explain why. It stays subordinate to conforming with the existing codebase, which always wins, and it is a writing standard, not a new gate. Prism deliberately kept these checks out of prism-gate.sh, because language-blind heuristics cry wolf, and a gate that cries wolf gets ignored.

05

Why the memory layer matters

Prism keeps a single file, .prism/project-model.md. It holds an evidence-cited model of the codebase: architecture, invariants (each cited), conventions, danger zones, a decision log, accumulated lessons, and the file concern map that routes the fan-out step. /prism-understand builds it, plan and build read it before they start, and implement and retro write back to it. Over time it becomes a sharper map, so future runs route work instead of rediscovering the same local context.

Just as important, Prism can prune. The /prism-prune command re-verifies cited invariants against the live code and corrects or deletes anything stale. That is what keeps the memory believable: it is re-checked against reality, not treated as permanently true.

06

Safety that is actually enforced

Prism takes safety more seriously than most agent systems, because it does not rely on telling the model to be careful. It uses real hooks.

The first, prism-guard.sh, is a PreToolUse hook that sits in front of one-way doors: force-pushes, publishes, deploys, database migrations, destructive deletes like rm -rf, and mainnet transactions. It blocks them unless the user explicitly approves with a # PRISM_OK token. The second, prism-gate.sh, runs inside /prism-implement and checks for fake-green work: skipped or deleted tests, hardcoded secrets, and leftover debug code, the things that make a build look passing when it is not.

If an action is expensive or impossible to undo, a reminder in a prompt is not enough. It needs a real gate in front of it, and Prism puts one there.

07

A full run, end to end

Here is what all of this looks like on a real question. Take the command /prism-plan how should users pay from their existing balance?

Prism reads it as a high-stakes planning task because it moves money, so it picks a looped eight-lens fleet and reads project memory first. Security goes into the auth and custody files, regulatory into the money-movement paths, data-integrity into the ledger and schema, each on its own code. The divergence line comes back 0.62, well past the 0.30 threshold, so the fan-out earned its cost. From there the judge rules on the conflicts, verification re-opens the cited lines and runs the skeptic panel, the loop runs to convergence, and the result is saved with its telemetry for a later /prism-retro to check against what actually happened.

08

The result that matters most

The last command, /prism-eval, makes the rest accountable. It runs against fixtures with known ground truth and reports four measurements: grounding precision and recall, a blind fleet-vs-single win rate, injected-flaw detection, and a find-the-floor sweep for the smallest fleet that still beats one pass. Anything not run reports as not run, never a guess.

That settles Prism's central bet: does fan out, judge, verify, and loop beat asking a strong model once? Every number below comes from a sub-agent that really ran, around 110 of them, with the token counts each reported. The battery was a blind A/B over twelve real design questions about Prism's own internals, none with an obvious answer: the skeptic ratio, the divergence weights, memory pruning, the rm -rf guard, loop convergence, and the rest.

The blind A/B used to test the bet. Labels were stripped and order alternated, with a "ignore length" instruction to the judge.

Over twelve tasks, a single careful pass beat the eight-lens fleet, at roughly a fifth of the cost.

The fleet lost. It won three tasks, the single careful pass won five, and four were ties, for a fleet win rate of 0.42 with a Wilson 95% interval of [0.19, 0.68], centered below even. It also cost far more: about 4.6 times the tokens, closer to 5.5 times counting one runaway agent. Paying roughly five times as much produced an answer that lost more often than it won. A four-task pilot had shown the fleet ahead three to nothing, but that lead collapsed under more data, which is exactly why the harness insists on at least twelve tasks and a confidence interval.

The most useful part of the result is where the fleet did win. All three of its wins came from a single lens catching a specific, concrete defect the single pass missed, including real bugs in Prism's own files: an adversary lens caught a math error in Prism's own rationale, where the claim that a lone Sonnet can decide "when both Opus miss" is impossible under majority-of-three; a safety lens found that prism-guard.sh:32 does not block a local git commit, leaving the branch step as the only thing keeping the agent off main; and the panel exposed an undefined-Jaccard hole in the divergence metric. But on open-ended design with nothing hidden to catch, one coherent deep pass matched or beat six fragmented briefs, and twice the single pass found a bug the fleet missed. The pattern is clear, and it is more useful than "multi-agent wins." Diversity pays when there is a sharp, concrete thing to catch, a contradiction or a bug or an unsupported claim, and adds little to broad design reasoning, where it is outweighed by the cost of splitting the work apart and stitching it back together.

Grounding, tested on its own, held up cleanly: fed eight claims, four true and four planted false, the verifier struck all four false and passed all four true, for precision and recall of 1.00. The caveat is that the fixture was easy, with fabricated line numbers and obvious contradictions, and n was only eight. It is a ceiling, not a stress test.

The confounds are disclosed, not buried. The fleet's answer in this run was hand-synthesised from six briefs under heavy load and carried its own defects, so some of the single pass's wins reflect bad synthesis rather than the method's true ceiling; in a real Prism run that synthesis is a fresh focused pass, which means this result understates the fleet. All twelve tasks were defect-free design questions, which under-represents the fleet's one measured strength. The single passes often ran longer and more thorough, and the instruction to ignore length only goes so far. There was one judge per task, with no position swap and no second judge, and n was twelve. The verdict the report commits to is careful: shrink-leaning, not proven.

09

Honest limitations

Two limits bound all of it. Prism is prompt-defined, not infrastructure: it rides Claude Code's agent loop, and the orchestration lives in prompts the model follows, with the hooks as the enforced exception. And its decorrelation is cross-tier, not cross-model, because pinning a genuinely separate model lineage is not available here, so the adversarial check still shares whatever blind spots are built into Claude. The recommendation that follows the numbers is to shrink the default fleet for open-ended design and reserve the full fleet for review and defect-finding. A firmer result would need a fixed fleet output instead of a hand-synthesis, position-swapped dual judges, and twenty-five or more tasks across more domains.

Production-grade means something specific here. Prism is markdown playbooks plus hooks plus memory, not a runtime, so dependable means trustworthy artifacts and disciplined process, not uptime. The remaining gaps are known and small: a write protocol so two runs do not clobber project-model.md, a version check for the copied playbooks, a safety guard re-sorted by reversibility (today prism-guard.sh over-blocks rm -rf node_modules and under-blocks a local git commit on main), a checkpoint.json per run for resume, and a four-tier evidence ladder with citation enforcement. Each one waits until an eval fixture proves it earns its cost.

10

How to use it

Using it is straightforward. Copy the command files into ~/.claude/commands/ for global use, or a repo's .claude/commands/ to share them with a team, wire the two hooks from the example settings, and then invoke /prism-* from any project. Every run states its plan up front, the archetype, mode, stakes, and fleet size, and prints a divergence line before it spends agents, so you can see what it is about to do and what the fan-out actually bought.

11

The real lesson

Prism does not prove that multi-agent AI is the future. If anything it points the other way: more agents should not be the default, and the gain from extra structure is narrower than the usual pitch claims. The reason the project is worth taking seriously is not the fleet. It is that Prism built the fleet, built the test, ran the test on itself, and kept a result that told it to spend less. That willingness to be wrong is rare, and it is what separates engineering from a demo.

White light enters a prism and splits into a spectrum. One question splits into a spectrum of expert perspectives, then recombines into one verified answer.
