01

Introducing Prism

A careful Claude Opus pass recently beat my eight-agent setup on five out of twelve design tasks. The eight-agent system performed better only three times, while the remaining four were ties. The single-agent pass also used around 4.6 times fewer tokens.

At first, that might sound like a disappointing result for a multi-agent system. For me, it was one of the most useful results Prism has produced. It is worth saying clearly that this was a small internal evaluation over twelve tasks, not a universal benchmark. But even at that scale it taught me something real.

It showed that adding more agents does not automatically produce better work. Sometimes a wider set of perspectives catches something important. Sometimes it adds cost and complexity without adding meaningful evidence. And sometimes one careful agent is simply better than a fleet that has to divide the problem and combine its conclusions later.

That result helped clarify what Prism should become.

Prism began as a multi-agent harness around Claude Code. But the more I tested it, the clearer the real problem became. The next bottleneck in coding agents is not their ability to generate more code. It is our ability to determine when their work can be trusted.

So Prism is now being developed as something more specific: an independent proof layer for AI-generated software, the verification step between a coding agent completing work and that work being accepted, merged or deployed. The rest of this article is about what that layer does, how it is built, and what the numbers say so far.

02

The problem is moving from generation to verification

Coding agents can already produce large volumes of plausible code quickly. Generation is no longer the scarce resource. The emerging problem is establishing whether that work is correct, grounded in the actual repository, current with the libraries it touches, and safe to ship.

A single pass through a strong model fails in predictable ways. It anchors on the first plausible answer and never stress-tests it. It states things about your code or a library's API that it never checked. It hands you a conclusion with no reasoning trail, so you cannot tell which parts to trust. And its confident tone is the same whether the claim is verified or invented, which is exactly the trap: confidence is not proof.

None of this means the agents are useless. It means the missing infrastructure sits after generation, not inside it. Someone has to reopen the files, rerun the tests, check the claims against current documentation, and decide what the change is actually worth. Doing that by hand does not scale with the volume agents now produce.

03

Prism is an independent proof layer

Prism sits between the agent that produced a change and the decision to trust it. In workflow terms:

Coding agent → proposed change → Prism verification → accept, human review or block
The agent that writes the code should not be the only system responsible for deciding whether that code is correct.

"Independent" here means Prism evaluates the work separately from the generation path. It does not reuse the generating agent's reasoning or take its claims at face value; it reopens the evidence and judges the change on what it finds. It does not mean cryptographic proof or mathematical certainty. The output is a structured, evidence-backed verdict, not a formal guarantee.

In one line, Prism is verification and evaluation infrastructure for coding agents. The current implementation is a set of slash commands, hooks and memory files that run inside Claude Code, where the project started. The architecture itself does not depend on which agent produced the change, and making the layer agent-independent is the direction the work is heading.

04

Evidence capture

Before any judgment, Prism assembles a case file for the change:

  • The requested task
  • The resulting diff
  • The agent's claims about its own work
  • The file:line references they rest on
  • Test results as run
  • Version-sensitive docs for the libraries involved
  • Project-specific architectural and security rules
  • Assumptions the agent left unresolved

Then it reopens the claims instead of trusting them. A claim about the code is checked against the current repository, opening the cited line to confirm it. A claim about an API is checked against current documentation or the installed type definitions, never the model's memory of a library that may have moved on.

05

Risk-based verification

Prism does not default to a large fleet. That is its most important design decision, and it came from the evaluation in the introduction. Every verification starts from the smallest useful path: a low-risk, well-grounded change, a rename or a small tested function, gets one verifier and a fast verdict. Specialists are added only when the change earns it, when it is high-risk, when its claims are poorly grounded, or when it crosses several system boundaries at once.

Verification cost then tracks the risk of being wrong. The expensive machinery exists for changes where a missed defect is costly, moving money, touching auth, altering schemas, and stays idle otherwise.

06

Differential evidence routing

When a change warrants specialists, the difference between them has to come from evidence, not job titles. Five agents given the same context with five role prompts produce five rephrasings of one opinion. Prism instead routes each verifier to the slice of the system its concern owns: on a payment feature, security reads authentication and custody, data integrity reads schemas and balances, UX follows the flow from intent to confirmation, cost reads infrastructure and fee surfaces. Each reports the exact file:line ranges it examined, so the verdict records what was looked at, not just what was concluded.

Prism also scores whether the routing worked. After a fan-out it measures how much the verifiers overlapped in the code they cited and how much their conclusions diverged. If they all read the same lines and said the same thing, the extra agents added nothing, and Prism says so rather than presenting the repetition as consensus.

07

Evidence judge and skeptic review

Independent verifiers will sometimes disagree, and the worst thing to do with a disagreement is average it into a vague middle. Prism does not average. A dedicated judge produces a structured resolution:

  • It resolves contradictions between verifiers instead of blending them
  • It identifies which conclusion the evidence better supports
  • It preserves useful findings that only one verifier caught
  • It surfaces blind spots the whole panel shared
  • It records uncertainty that could not be resolved, rather than papering over it

Conclusions that carry real weight then face one more round: skeptic agents whose only job is to refute them. In the current implementation the panel is two Opus instances and one Sonnet under majority rule, chosen from different Claude tiers to reduce the odds that all reviewers share the same error. Prism is careful about what surviving this means. A claim that was re-checked against live code or current docs is labeled grounded; a claim that merely survived the skeptics ranks below it. "We checked this" and "nobody objected to this" are different statements, and every output keeps them apart.

08

The Proof Packet

Everything above funnels into one artifact, and it is the thing Prism actually produces: the Proof Packet. Not a chat transcript, not another agent-generated summary that itself needs verifying, but a structured record of the verification. It answers six questions:

Proof Packet · contents
Verified: what was actually checked, and what was out of scope
Evidence: which files, lines, docs and rules were examined
Tests: which passed, which failed, which never ran
Assumptions: what remains unresolved and would change the verdict
Risks: what was found, with severity and location
Verdict: accept, send to human review, or block

The packet is what a reviewer reads instead of re-deriving the whole change from scratch, and what a team can point to later when asking why something was merged. If Prism is a proof layer, the Proof Packet is the proof.

Verification is only useful if the system can carry its conclusions forward and enforce them. That is where Prism's memory and safety layers come in.

09

Revalidated project memory

Prism keeps structured project knowledge in a single file, .prism/project-model.md: the architecture, the invariants the code must hold, the conventions it follows, previous decisions and their reasoning, the danger zones where mistakes are expensive, and concerns that were raised but never resolved. Verification reads this before judging a change, so a diff that quietly violates a recorded invariant gets caught even when it looks locally fine.

Memory like this is only useful if it stays true, and codebases drift. So Prism treats stored knowledge as claims to recheck, not facts to trust. The /prism-prune command re-verifies recorded invariants against the current repository and corrects or deletes anything stale. Nothing in the model is treated as permanently correct; it is believable precisely because it keeps getting re-earned.

10

Enforced safety

Some conclusions are too important to live as advice in a prompt, because text three hundred lines into a context window is easy to ignore. Prism enforces its hard limits with hooks that run outside the model.

Prism Guard blocks force-pushes, deployments, destructive migrations, dangerous deletes and mainnet transactions until they are explicitly approved. It is a PreToolUse hook (prism-guard.sh) that sits in front of these one-way doors and requires an explicit # PRISM_OK token from the user before any of them open.

Prism Gate detects fake-green work, including skipped tests, exposed secrets, debug leftovers and incomplete implementations presented as finished. It runs inside the implementation loop (prism-gate.sh) and exists for the specific failure mode where a build looks passing because the tests that would have failed were quietly skipped or deleted.

If an action is expensive or impossible to undo, a reminder is not enough. It needs a real gate in front of it, and Prism puts one there.

11

Measuring whether more agents helped

A verification system that never verifies itself would be an odd thing to trust, so Prism ships an evaluation harness, /prism-eval, that measures whether its own structure earns its cost. It can evaluate:

  • Grounding quality: precision and recall on claims checked against known ground truth
  • Injected-flaw detection: whether planted defects get caught
  • Fleet-versus-single performance: blind A/B comparison against one careful pass
  • Cost and token usage: what the extra structure actually spends
  • The smallest fleet: the minimum configuration that still produces a measurable improvement

The headline run so far is the one this article opened with: a blind A/B over twelve real design questions about Prism's own internals, judged with labels stripped and order alternated. Every number came from a sub-agent that really ran, with the token counts each reported.

A small internal evaluation, not a universal benchmark: twelve design tasks, one blind judge per task.

The fleet won three tasks, the single careful pass won five, and four were ties, a fleet win rate of 0.42 with a Wilson 95% interval of [0.19, 0.68]. The fleet also cost about 4.6 times the tokens. An early four-task pilot had shown the fleet ahead three to nothing; that lead collapsed under more data, which is exactly why the harness insists on at least twelve tasks and a confidence interval before believing anything.

The most useful part of the result is where the fleet did win. All three of its wins came from a single verifier catching a specific, concrete defect the single pass missed, including real bugs in Prism's own files: a math error in its own rationale, a gap in prism-guard.sh, and an undefined-value hole in one of its metrics. On open-ended design questions with nothing hidden to catch, one coherent pass matched or beat the divided briefs, and twice found a bug the fleet missed.

The honest conclusion: multi-agent verification appears most helpful when there is something concrete to catch, a contradiction, a bug, an unsupported claim, while one coherent pass may perform better for broad, open-ended design. Grounding, tested separately, went eight for eight on planted true and false claims, though on a small and deliberately easy fixture; that is a ceiling, not a stress test. These results shaped the risk-based defaults in section 5: start small, escalate only when the change gives a reason to.

12

Less agent theater, more proof

The direction Prism is heading is away from celebrating orchestration and towards making verification legible. The goal is not to show how many agents were spawned. The goal is to show what was checked, which evidence supports the result, what remains uncertain and why the work is safe to accept.

Less agent theater. More proof.

That is the direction I am building towards with Prism.
