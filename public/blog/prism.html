Prism · multi-agent harness for Claude Code

A multi-agent harness that measures its own value

A complete agent workflow, from reading a codebase to shipping and reviewing it, built on grounded claims, compounding memory, and enforced safety. And a rare experiment: does the fleet actually beat one careful pass?

  • grounded
  • stateful
  • enforced
  • falsifiable

The bet nobody checks

Most multi-agent AI tools rest on one assumption: if one model is useful, a coordinated group should be better. So people add roles. One agent plans, another critiques, another verifies, and the hope is that more perspectives produce a better answer.

It sounds right. Almost nobody checks.

Prism checks. It is a multi-agent orchestration harness for Claude Code: a set of slash commands that take a hard problem, split it across several agents that look at different evidence, judge where they disagree, verify the claims that matter, and loop until the answer settles. That much is familiar. What makes Prism unusual is the system around that loop. It remembers the project across runs, grounds every claim in real code, enforces its safety rules with hooks the model cannot skip, and ships a harness that measures whether the whole multi-agent apparatus actually beats a single careful pass.

When it ran that measurement on its own design, the result was uncomfortable. Across twelve real design tasks about Prism's own internals, one careful Opus pass beat the eight-agent setup five times, lost three, and tied four, at about 4.6 times fewer tokens.

Prism reports that plainly and keeps building from it. This article is about the whole system, not just the scoreboard. A strong model alone is already capable: it can plan, explain, critique, and write working code, so anything that wraps extra agents around it has to earn the cost and the complexity it adds. Prism holds itself to exactly that standard.

The problem it starts from

One pass through a strong model fails in a handful of predictable ways. It anchors on the first answer that sounds right and never stress-tests it. It averages two real but conflicting considerations into a vague middle instead of deciding which one wins. It hallucinates with confidence, stating things about your own code or a library's API that it never checked. It hands you a conclusion with no reasoning trail, so you cannot tell which parts to trust. It is stateless, relearning the same project facts every session. Its safety guidance is unenforced, just text it can ignore three hundred lines into a session. And the usual multi-agent cure for all of this is unfalsifiable, because the tools selling it never measure whether the agents helped.

Each of those failure modes has a specific answer in the sections below. Two ideas organize the whole design: the agents are made to look at different evidence rather than wear different hats, and conflicts between them are decided, not blended into a vague middle.

The nine commands

Prism is not one prompt. It is a workflow, and each stage of that workflow is its own command.

The heavy commands (plan, build, implement, and feedback) all run on one shared engine. That engine is where most of Prism's interesting decisions live.

The deliberation engine

Every heavy command feeds the same pipeline: fan out across lenses, score how much they diverged, judge the results, verify the claims that matter, loop until the answer stops changing, and persist what was learned. Here is the lifecycle and the engine together.

Fan-out with differential context. Prism launches several agents in parallel, each a distinct lens, but the important move is that they do not all get the same context. The core lenses (first-principles, adversary, practitioner) stay holistic and look at the whole problem. The domain lenses are routed to the slice of code their concern owns: the security lens reads auth, keys, and custody; the regulatory lens reads the money-movement paths; the data-integrity lens reads the schema and ledger; the cost lens reads fees and infrastructure; the UX lens reads the user flows. Each lens reports the exact file:line ranges it examined. This is what separates real diversity from theater. Many multi-agent systems are one model in different hats, reading identical context and unsurprisingly agreeing. Prism forces the lenses to look at different evidence, and it caches the routing as a file concern map in memory so it does not have to rediscover which files matter on every run.

Divergence score. Right after fan-out, Prism checks whether the lenses truly split or only appeared to. It computes a score: 0.6 x (1 minus the mean Jaccard overlap of the cited file:line sets) + 0.4 x (conclusion disagreement). The overlap term carries the most weight on purpose, because it directly tests whether the differential routing worked. If the lenses cited the same lines and reached the same conclusion, the extra agents added nothing, and Prism says so. The metric prints on every run and flags when the diversity is only cosmetic. The threshold itself is a deliberate placeholder, set to 0.30 and marked uncalibrated until the proof harness derives a real cutoff from data. It is a falsifier aimed squarely at Prism's own premise.

Judge. The judge does not blend the briefs into an average. It produces a structured read: what the lenses agree on, where they contradict each other and which side is better supported, which insights only one lens caught, and which blind spots they all share. The output is a decision, not a merge.

Verify, in two checks. First, grounding. Every claim about the code has to cite a file:line, and a verifier re-opens that line to confirm it. Every claim about a library or API is checked against installed type definitions or official docs, never the model's memory. Second, adversarial review. Each load-bearing claim is handed to a panel of skeptics whose job is to refute it: two Opus instances for rigor and one Sonnet for independence, under majority rule, so two of three votes kill a claim. The split is deliberate. The lone Sonnet cannot sink a good claim on its own, but it can be the deciding vote on a flaw both Opus instances missed.

Loop and persist. Prism then re-attacks its own draft in critique mode, folds in only the fixes that survive, and repeats until a full round changes nothing material. That convergence loop is capped at three rounds so it cannot spin forever. The final result is saved to docs/, the project memory is updated, and a telemetry block is attached that records the divergence score, the model pool that ran, and how each claim survived.

One caveat about that verification, because Prism insists on stating it. The skeptic panel uses different Claude tiers, not different model families. The sub-agent setting selects by tier only, so this is cross-tier review, not cross-version and certainly not cross-model. Surviving the skeptics is labeled cross-tier-survived, and that label ranks below grounded, which means re-checked against live code or docs. Every decision doc Prism writes carries the caveat in plain text: cross-tier review lowers the chance that all the reviewers share the same error, but it does not remove the blind spots baked into Claude itself, so cross-tier survival is weaker evidence than grounding. A lot of AI systems quietly blur "we checked this" with "nobody objected to this." Prism keeps the two apart.

Why the memory layer matters

One of Prism's most useful pieces is its project memory, and it is what makes the system stateful instead of starting cold every time.

Prism keeps a single file, .prism/project-model.md, that holds an evidence-cited model of the codebase: its architecture, its invariants with a citation for each, its conventions, its danger zones, a decision log, accumulated lessons, and the file concern map that tells the fan-out step which files belong to which concern. /prism-understand builds this model, the planning and building commands read it before they start, and implement and retro write back to it. Over time it becomes a sharper map of the project, and that map lets future runs route work more intelligently instead of rediscovering the same local context.

Most AI coding tools forget too much and burn time relearning the same facts. Prism tries to keep what matters. Just as important, it can prune. The /prism-prune command re-verifies cited invariants against the live code and corrects or deletes anything that has gone stale. That is what keeps the memory believable. It is not treated as permanently true. It is re-checked against reality.

Safety that is actually enforced

Prism takes safety more seriously than most agent systems, because it does not rely on telling the model to be careful. It uses real hooks.

The first, prism-guard.sh, is a PreToolUse hook that sits in front of one-way doors: force-pushes, publishes, deploys, database migrations, destructive deletes like rm -rf, and mainnet transactions. It blocks them unless the user explicitly approves with a # PRISM_OK token. The second, prism-gate.sh, runs inside /prism-implement and checks for fake-green work: skipped or deleted tests, hardcoded secrets, and leftover debug code, the things that make a build look passing when it is not.

The instinct is the right one. If an action is expensive or impossible to undo, a reminder in a prompt is not enough. It needs a real gate in front of it, and Prism puts one there.

The proof harness

The last command, /prism-eval, is the one that makes the rest accountable. It runs against fixtures with known ground truth and produces four measurements: grounding precision and recall, tested against known invariants plus injected false and stale claims; a blind fleet-vs-single win rate over a task battery; injected-flaw detection, where the fleet and a single pass both review a planted bug; and a find-the-floor sweep that reports the smallest configuration that still beats a single pass. Any section that was not run reports as not run rather than being filled in with a guess.

A full run, end to end

Here is what all of this looks like on a real question. Take the command /prism-plan how should users pay from their existing balance?

Prism classifies it as a planning task that is high-stakes because it moves money, so it picks a looped eight-lens fleet and reads project memory first. The differential fan-out sends the security lens into the auth and custody files, the regulatory lens into the money-movement paths, and the data-integrity lens into the ledger and schema, each on its own code, each reporting the lines it touched. The divergence line comes back as 0.62 (evidence 0.71, conclusion 0.48) against the uncalibrated 0.30 threshold, high enough to confirm the lenses truly diverged and the fleet is doing real work; a low score here would have been flagged as cosmetic. The judge reconciles the agreement, rules on the contradictions, and collects the unique catches and shared blind spots. The draft comes out in a fixed expert format: the recommendation, the reasoning behind it, a steelman of the option it rejected, the assumptions it depends on and what would falsify them, the open questions, and grounded citations. Verification re-opens the cited lines, checks any SDK calls against their docs, and runs the skeptic panel on each load-bearing claim. Critique rounds run until convergence, the result is saved with its telemetry block, and a later /prism-retro compares what was predicted against what happened and banks a measured lesson.

The result that matters most

That brings us to the test. Prism's entire premise is a single bet: fan out, judge, verify, and loop beats asking a strong model once. The /prism-eval harness exists to settle that bet under one rule, no fabrication. Every number below comes from a sub-agent that was really run, around 110 of them, with token counts each agent reported. The battery was a blind A/B over twelve real design questions about Prism's own internals, none with an obvious answer: the skeptic ratio, the divergence weights, memory pruning, the rm -rf guard, loop convergence, and more.

The fleet lost. It won three tasks, the single careful pass won five, and four were ties, for a fleet win rate of 0.42 with a Wilson 95% interval of [0.19, 0.68], centered below even. It also cost far more: about 4.6 times the tokens, closer to 5.5 times counting one runaway agent. Paying roughly five times as much produced an answer that lost more often than it won. A four-task pilot had shown the fleet ahead three to nothing, but that lead collapsed under more data, which is exactly why the harness insists on at least twelve tasks and a confidence interval.

The most useful part of the result is where the fleet did win. All three of its wins came from a single lens catching a specific, concrete defect the single pass missed, including real bugs in Prism's own files: an adversary lens caught a math error in Prism's own rationale, where the claim that a lone Sonnet can decide "when both Opus miss" is impossible under majority-of-three; a safety lens found that prism-guard.sh:32 does not block a local git commit, leaving the branch step as the only thing keeping the agent off main; and the panel exposed an undefined-Jaccard hole in the divergence metric. But on open-ended design with nothing hidden to catch, one coherent deep pass matched or beat six fragmented briefs, and twice the single pass found a bug the fleet missed. The pattern is clear, and it is more useful than "multi-agent wins." Diversity pays when there is a sharp, concrete thing to catch, a contradiction or a bug or an unsupported claim, and adds little to broad design reasoning, where it is outweighed by the cost of splitting the work apart and stitching it back together.

Grounding, tested on its own, held up cleanly: fed eight claims, four true and four planted false, the verifier struck all four false and passed all four true, for precision and recall of 1.00. The caveat is that the fixture was easy, with fabricated line numbers and obvious contradictions, and n was only eight. It is a ceiling, not a stress test.

And the confounds are disclosed rather than buried, which is the part that makes the number trustworthy. The fleet's answer in this run was hand-synthesised from six briefs under heavy load and carried its own defects, so some of the single pass's wins reflect bad synthesis rather than the method's true ceiling; in a real Prism run that synthesis is a fresh focused pass, which means this result understates the fleet. All twelve tasks were defect-free design questions, which under-represents the fleet's one measured strength. The single passes often ran longer and more thorough, and an instruction to ignore length only goes so far. There was one judge per task, with no position swap and no second judge, and n was twelve. The verdict the report commits to is careful: shrink-leaning, not proven.

Honest limitations

Two limits bound all of it. Prism is prompt-defined, not infrastructure: it rides Claude Code's agent loop, and the orchestration lives in prompts the model follows, with the hooks as the enforced exception. And its decorrelation is cross-tier, not cross-model, because pinning a genuinely separate model lineage is not available here, so the adversarial check still shares whatever blind spots are built into Claude. The recommendation that follows the numbers is to shrink the default fleet for open-ended design and reserve the full fleet for review and defect-finding. A firmer result would need a fixed fleet output instead of a hand-synthesis, position-swapped dual judges, and twenty-five or more tasks across more domains.

How to use it

Using it is straightforward. Copy the command files into ~/.claude/commands/ for global use, or a repo's .claude/commands/ to share them with a team, wire the two hooks from the example settings, and then invoke /prism-* from any project. Every run states its plan up front, the archetype, mode, stakes, and fleet size, and prints a divergence line before it spends agents, so you can see what it is about to do and what the fan-out actually bought.

The real lesson

Prism does not prove that multi-agent AI is the future. If anything it points the other way: more agents should not be the default, and the gain from extra structure is narrower than the usual pitch claims. The reason the project is worth taking seriously is not the fleet. It is that Prism built the fleet, built the test, ran the test on itself, and kept a result that told it to spend less. That willingness to be wrong is rare, and it is what separates engineering from a demo.

White light enters a prism and splits into a spectrum. One question splits into a spectrum of expert perspectives, then recombines into one verified answer.
